# PreChess — план реализации

**Статус:** рабочий план  
**Обновлено:** 2026-09-26  
**Главный продуктовый документ:** `docs/product/prediction-market.md`

Этот документ отвечает на один вопрос:

> **Что именно нужно сделать и в каком порядке, чтобы из текущего состояния репозитория получить тестируемый MVP PreChess?**

Главный принцип: сначала доказать механику рынка на записанных партиях, потом подключать live-данные и только после этого строить полноценный мобильный UX.

Нельзя начинать с красивого приложения и потом пытаться «подложить» под него механику. Самый большой риск проекта сейчас — не интерфейс, а качество рынков, корректность расчёта и поведение AMM.

# 1. Построить шахматный Event Engine

## Цель

Научиться превращать каждый ход партии в набор объективных шахматных событий.

Это фундамент всей системы.

## Вход

- FEN до хода;
- ход;
- FEN после хода;
- история партии.

## Выход

Структурированный `ChessEvent`.

Пример:

```text
ply: 27
move: Bxh7+
events:
  capture: true
  check: true
  captured_piece: pawn
  mover: white
```

# 4. Построить Market Generator

## Цель

На каждом ходу выбирать не все технически возможные рынки, а только несколько действительно интересных.

## Первая версия

Без LLM и без сложной модели.

Только:
- правила;
- признаки позиции;
- история уже показанных рынков;
- Stockfish как дополнительный сигнал.

## TODO

- [ ] Рассчитывать признаки:
  - [ ] ожидаемая близость развязки;
  - [ ] неопределённость;
  - [ ] связь с текущей позицией;
  - [ ] понятность;
  - [ ] повторяемость;
  - [ ] схожесть с другими активными рынками.
- [ ] Сделать первый простой scorer.
- [ ] Добавить ограничение:
  - [ ] 1 короткий;
  - [ ] 1 средний;
  - [ ] 1 длинный рынок.
- [ ] Не показывать повторно один шаблон без существенного изменения позиции.
- [ ] Подключить Stockfish как дополнительный источник признаков.
- [ ] Не использовать Stockfish как прямой источник вероятности человеческого хода.

## Проверка

Прогнать генератор минимум по нескольким сотням партий и вручную посмотреть выбор рынков.

## Метрики качества генератора

- сколько рынков имеют реальную развязку в заявленном горизонте;
- сколько рынков оказываются почти очевидными;
- сколько повторяются;
- сколько выглядят бессмысленными для человека;
- среднее время до расчёта.

## Результат этапа

На любом ходу система умеет выбрать 2–3 разумных вопроса, которые действительно хочется прогнозировать.

## Сценарий

```text

→ блокировка
→ резолв
→ settlement
→ обновление баланса
→ новый рынок
```

# 16. Закрытая альфа

## Цель

Проверить не «работает ли код», а «хочется ли продолжать прогнозировать».

## Формат

20–50 пользователей, которые понимают шахматы.

## Наблюдать

- понимают ли они цену без объяснений;
- понимают ли доли;
- замечают ли движение рынка;
- интересно ли смотреть следующие ходы после сделки;
- хочется ли сразу участвовать в следующем рынке;
- какие вопросы раздражают или кажутся бессмысленными;
- слишком много или слишком мало рынков;
- предпочитают ли short markets рынку победителя.

## Gate 2

Продолжаем развитие только если повторяющийся цикл:

`прогноз → наблюдение → развязка → новый прогноз`

реально заставляет людей оставаться в партии и делать следующий прогноз.

# Что можно делать параллельно

После фиксации правил MVP:

**Поток A — шахматная механика**
- Event Engine;
- Replay;
- Resolver;
- Generator.

**Поток B — рынок**
- LMSR;
- симуляции;
- параметры ликвидности.

**Поток C — дизайн**
- мобильный UX;
- интерактивный прототип;
- тест понимания price/shares/P&L.

Но полноценный backend и финальную схему данных нельзя фиксировать до результатов потоков A и B.

# Что сейчас НЕ делать

Пока не пройдены первые продуктовые тесты:

- не строить сложную авторизацию;
- не делать красивый профиль;
- не делать социальную сеть;
- не добавлять другие виды спорта;
- не делать реальные деньги;
- не строить order book;
- не делать генерацию рынков через LLM;
- не оптимизировать инфраструктуру под огромный трафик;
- не писать большой backend до фиксации LMSR и контрактов рынков.
